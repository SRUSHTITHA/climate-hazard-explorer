# working.md

## 1. Brief

Problem Statement

Build a web application that analyzes historical weather data and visualizes trends in climate hazards, such as heatwaves, droughts, or heavy rainfall events, for a selected region over time.

Key Features

Frontend (React)
Allow users to:
- Select a geographic region (city, state, or a custom lat-lon box).
- Use Heatwave as the hazard type, selected by default.
- Choose a time range (e.g. 1990-2020).
Display:
- Time-series plots of hazard frequency/intensity.
- Interactive visualizations (e.g. charts, maps).
- Summary insights such as "Heatwaves have increased by 40% in this region since 1990."

Backend (Python)
Ingest and cache historical weather data from public APIs such as:
- NOAA NCEI
- Copernicus Climate Data Store
- Open-Meteo API
- Or any other source
Define logic to detect climate hazards:
- Example (Heatwave): 3+ consecutive days with maximum temperature above the 95th percentile for that region.
- Analyze frequency and duration trends using rolling averages or regression.
- Store this data in a NoSQL database.
- On an API call, read this data from the database and return JSON summaries and trend plots.

Evaluation Dimensions

| Dimension | What we look for | Weight |
|---|---|---|
| Data Handling | Working with real-world noisy, inconsistent data: gaps, outliers, units, caching | 20% |
| Climate Logic | Ability to define and apply domain-specific rules (e.g. a percentile-based heatwave definition) | 20% |
| Backend Skills | Efficient data processing, clean API design, safe external API access | 20% |
| Frontend Skills | Clear, interactive visualization using Chart.js, D3.js, or similar | 15% |
| Critical Thinking | Deriving sound, honest insight from climate indicators | 10% |
| Security + Performance | API caching, rate-limiting, and safe handling of user inputs | 15% |

Optional (attempt only after the core features work)
- Use a map UI (e.g. Leaflet or Mapbox) for region selection.
- Provide PDF/CSV export of insights.
- Apply trend detection techniques such as linear regression or the Mann-Kendall test.

## 2. Locked Decisions
- Data source: Open-Meteo archive API (ERA5 reanalysis, ~0.25 degree grid), variable temperature_2m_max, units Celsius, explicit timezone parameter. Host is hardcoded in code, never user-supplied. Request parameters are fixed: daily=temperature_2m_max, temperature_unit=celsius, timezone=auto, models=era5. ERA5 is pinned because the default "Best match" blends ECMWF IFS 9 km data from 2017 onward, which would introduce an artificial discontinuity in a multi-decade series; Open-Meteo's documentation recommends ERA5 or ERA5-Land only for climate-change studies. cell_selection and elevation are left at their defaults.
- Ingest window: 1990 through the last complete calendar year. Whole history fetched once per grid cell, in chunks.
- Grid: coordinates snapped to 0.25 degrees. cell_id format "{lat:.2f}_{lon:.2f}" using snapped values.
- Region input: point (city, state preset, geocoded place) or box. A box resolves to the set of grid cells inside it. Hard cap: 9 cells, otherwise HTTP 422.
- Baseline for thresholds: 1991-2020, always, regardless of the user's selected range.
- Selectable range: 1990 to last complete year, minimum span 10 years.
- Day index: leap-aligned day of year, 1..366, where Mar 1 is always 61 (Feb 29 occupies slot 60 only in leap years).
- Threshold: per day-index, 95th percentile (numpy nanpercentile, linear interpolation) of tmax over baseline years within a circular +/-7 slot window.
- Heatwave: 3 or more consecutive days with tmax strictly greater than that day's threshold. A missing value breaks a run. Events are detected on the continuous multi-year series and assigned to the year of their start date.
- Year validity: at least 90% non-null days. Invalid years are excluded from metrics and trends and listed in the quality report.
- Physical validity bounds: -90.0 to 60.0 degrees Celsius inclusive. Values outside, non-finite values, and non-numeric values are invalid and become NaN.
- Suspect flag (flag only, never removed): absolute deviation greater than 15 degrees Celsius from the centred 15-day rolling median (min_periods 8).
- Missing values and missing dates are never imputed.
- Annual metrics: event_count, heatwave_days, longest_event_days, mean_duration_days, mean_intensity_c (mean exceedance over threshold), season_start_doy, season_end_doy.
- Region metrics: mean of per-cell annual metrics across valid cells.
- Trend: Theil-Sen slope (scipy) of heatwave_days per year, reported per decade; Mann-Kendall (pymannkendall) p-value; 5-year centered rolling mean with min 3 periods.
- Confidence: needs at least 15 valid years or result is "insufficient data". p < 0.05 "strong evidence", 0.05 to 0.15 "weak evidence", otherwise "no clear trend".
- Percent change: only when the first-5-year mean is at least 1.0 days per year; otherwise report absolute change.
- Insights are produced by deterministic code, never by an LLM.
- Backend: Python 3.11+, FastAPI sync endpoints, httpx sync, pymongo, pandas, numpy, scipy, pymannkendall, pydantic v2 and pydantic-settings, slowapi. Tests: pytest, mongomock. Lint: ruff.
- Frontend: Vite, React, plain JavaScript, Chart.js via react-chartjs-2, TanStack Query, Leaflet for the optional map. State lives in URL query params.
- Hosting: frontend on Vercel or Netlify, backend on Render, database on MongoDB Atlas M0.

## 4. Data Contracts (MongoDB)
- raw_daily: one doc per cell-year. {cell_id, year, source, fetched_at (UTC-aware datetime), unit ("C"), grid_lat, grid_lon, elevation (nullable), utc_offset_seconds, tmax (list of float or null, length exactly 365 or 366 for that calendar year), valid_days, total_days, quality: {missing_days, invalid_days, suspect_days}}. Unique index (cell_id, year). NaN is never stored; it is stored as null.
- thresholds: {cell_id, baseline_start, baseline_end, window_days, percentile, hazard, values: [366 floats or null], computed_for_last_full_year, created_at}. Unique index on the first five fields; one doc per cell-baseline. NaN is stored as null and restored as NaN on read.
- events: {cell_id, hazard, year, start, end, duration_days, peak_tmax, mean_tmax, intensity, max_exceedance, computed_for_last_full_year, created_at}. start/end are ISO date strings; unique index (cell_id, hazard, start) (event identity is its start date, so a year may hold more than one event).
- annual_metrics: {cell_id, hazard, year, valid_days, total_days, valid, event_count, heatwave_days, max_duration, mean_duration, mean_intensity, max_exceedance, peak_tmax, computed_for_last_full_year, created_at}. Unique index (cell_id, hazard, year); one doc per year including invalid years. Floats are stored null when NaN.
- analyses: {key, region, cell_ids, hazard, start_year, end_year, computed_for_last_full_year, created_at, result}. key is the sha256 hex of the canonical JSON of (hazard, sorted cell_ids, start_year, end_year, last_full_year); result is the serialised AnalysisResponse. Unique index on key plus a TTL index on created_at (7 days, UTC-aware datetime).

### API Contracts
- GET /health -> always HTTP 200 with body {"status": "ok", "database": "up"|"down"}. "up" only when db.command("ping") succeeds; exceptions are swallowed, never leaked in the response. The endpoint never returns non-200 and never reveals the exception text.
- GET /analysis (Task 14) accepts the flat query model `AnalysisRequest`: hazard is the single literal "heatwave" (default heatwave); start_year >= HISTORY_START (1990); end_year >= start_year; span (end_year - start_year + 1) >= 10; exactly one region shape - point (lat, lon) or box (south, west, north, east) with south < north and west < east; all coordinates finite and within lat [-90, 90] / lon [-180, 180]; a box resolving to more than 9 grid cells is rejected. Unknown fields are rejected (extra="forbid"). The clock-dependent upper bound (last complete calendar year) is NOT enforced by the model; Task 14 enforces it.
- AnalysisResponse body: {hazard, cell_ids[], start_year, end_year, series[YearPoint], trends{metric: TrendOut}, insights[InsightOut], quality{valid_years, total_years, cells, min_cells_valid}, attribution}. The trend metric keys are exactly heatwave_days and mean_intensity. TrendOut is exactly the eight keys of `trends.trend`; YearPoint mirrors the `metrics.region_metrics` columns plus rolling_heatwave_days. Every float field is JSON null rather than NaN/Infinity, so a response is always strict JSON.
- ErrorResponse body: {code (lower snake-case machine string), message (bounded, never containing a URL, path, database URI or stack trace)}.
- Error status/code map (Task 15): 400 `invalid_request` (validation failure), 404 `not_found`, 405 `method_not_allowed`, 429 `rate_limited`, 500 `internal_error`, 502 `data_unavailable`, 503 `database_unavailable`, any other Starlette status -> `http_error`. Every error body is an ErrorResponse.
- Response headers (Task 15): `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` on every response; `Cache-Control: no-store` on `/health`, on every status >= 400 and on every 429; `ETag` plus `Cache-Control: public, max-age=3600` on a 200 `GET /api/analysis` (a matching `If-None-Match` returns 304 with an empty body); `Retry-After` and the `X-RateLimit-*` family on a 429. Limits default to `120/minute` for general routes and `30/minute` for `GET /api/analysis` (configurable via `RATE_LIMIT_DEFAULT`/`RATE_LIMIT_COMPUTE`).
- CORS (Task 15): methods `GET, OPTIONS`; request header `If-None-Match`; exposed response headers `ETag, Retry-After`; credentials disabled; origins from `CORS_ALLOWED_ORIGINS` (empty means no cross-origin origin is allowed).

### Upstream Contract
- Request (GET https://archive-api.open-meteo.com/v1/archive), exactly eight params: latitude, longitude (from regions.cell_center), start_date "YYYY-01-01", end_date "YYYY-12-31", daily=temperature_2m_max, temperature_unit=celsius, timezone=auto, models=era5. No api key on the free tier. Redirects not followed.
- Response fields observed in the three real calls: latitude, longitude, generationtime_ms, utc_offset_seconds, timezone, timezone_abbreviation, elevation, daily_units {time, temperature_2m_max}, daily {time: [ISO dates], temperature_2m_max: [numbers with null for missing]}. daily_units.temperature_2m_max is literally "°C".
- With models=era5 the response latitude/longitude equal the requested coordinates exactly (call 1: 28.5, 77.25). Without models (default Best match) they are the nearest ~9 km IFS grid point (call 2: 28.50615, 77.20136). Error responses are HTTP 400 with body {"error": true, "reason": "..."} (call 3).

## 6. Domain Notes
- Fixed 0.25-degree grid as cache key: adjacent or overlapping requests snap to the same cell_ids, so cached raw data and thresholds are shared across requests and the fan-out of upstream Open-Meteo calls per request is bounded. The grid is the identity of cached data, not a projection; it exists for determinism and cache reuse.
- Cap of 9 cells per region: limits upstream calls and per-request compute, protecting the free API tier and bounding response latency. The cap is checked from index counts before any list is built, so absurd boxes (e.g. the whole world) are rejected in microseconds, not enumerated.
- Half-up rounding (floor(v/0.25 + 0.5) * 0.25) is deterministic and free of banker's-rounding surprises; Python's round() uses round-half-even, which would make tie behaviour depend on the parity of the preceding digit. Negative zero is normalised so IDs are "0.00" and never "-0.00".
- Antimeridian: boxes crossing longitude 180/-180 (west > east) are intentionally unsupported; every cell_id is still a legal lon in [-180, 180], and any grid near the antimeridian is addressable by individual cell_id.
- Verified against Open-Meteo docs (https://open-meteo.com/en/docs/historical-weather-api): the Historical Weather API resolves a requested coordinate to the nearest model grid cell; the response's latitude/longitude are "WGS84 of the center of the weather grid-cell which was used to generate this forecast. This coordinate might be a few kilometres away from the requested coordinate." ERA5 is listed as Global, 0.25 deg (~25 km), hourly, 1940-present. So our 0.25-degree cache grid matches the ERA5 native grid, and the resolved cell center is what the API actually returns for tmax.
- Locked Decision amendment, 2026-10-11 (Task 04): pinned models=era5. Open-Meteo's default "Best match" combines ECMWF IFS (9 km) from 2017 onward with ERA5 before that, which would inject a resolution change mid-series and fake a trend; the docs explicitly advise using ERA5 or ERA5-Land only for climate-change studies over decades. Pinning era5 keeps one homogeneous model across 1990-present.
- ERA5 homogeneity: a single reanalysis product at fixed 0.25-degree resolution with a consistent assimilation system means year-to-year differences reflect weather/climate, not model changes. This matters because the whole product is about multi-decade trends, where a model discontinuity would dominate the signal.
- ERA5's native 0.25-degree grid coincides with our cache grid: with models=era5 the archive API returned exactly the requested snapped coordinates (28.5, 77.25), so one cell_id maps to exactly one ERA5 grid point and cached data cannot be silently served for a different upstream cell.
- Daily maxima are aggregated on the timezone's calendar-day boundaries. With timezone=auto the UTC offset is resolved once, at request time, and any DST change inside the requested range is ignored (documented by Open-Meteo). Accepted limitation: a one-hour shift moves the 24-hour window by an hour, which has a negligible effect on a daily maximum (and our ingest window is whole years).
- The returned grid cell can sit a few km from the requested point. Observed in the pasted real responses: call 2 (default Best match) requested (28.5, 77.25) and returned (28.50615, 77.20136), a great-circle distance of 4.802 km; call 1 (models=era5) returned the requested point exactly (0 km). This is why the client stores grid_lat/grid_lon from the response rather than assuming the request coordinates.
- Open-Meteo free-tier limits (read 2026-10-11 from https://open-meteo.com/en/pricing and https://open-meteo.com/en/terms): 600 calls/minute, 5,000 calls/hour, 10,000 calls/day, 300,000 calls/month; free tier is non-commercial use only. The Historical Weather API is available on the free tier.
- Attribution (read 2026-10-11 from https://open-meteo.com/en/licence): API data are offered under CC BY 4.0, which mandates giving appropriate credit and indicating modifications. Open-Meteo requires a link next to any location where its data is displayed, e.g. `<a href="https://open-meteo.com/">Weather data by Open-Meteo.com</a>`. The underlying ERA5 reanalysis comes from Copernicus Climate Change Service (C3S) and must also be acknowledged. Server code is AGPLv3; the data licence is what binds us.
- Statistical outliers are flagged, never removed: in a heatwave study the extreme days are the signal, not noise. Dropping a suspect 50 C day would bias event counts and mean exceedance intensities downward; keeping it lets the event logic (Task 07) decide, with the suspect flag available as context.
- No imputation: interpolation across a missing day could create or erase consecutive above-threshold runs - hand-inserting a plausible 34 C instead of 29 C decides whether a heatwave "happened". Instead, a missing day stays a gap (a run is inherently broken) and metrics stay honest.
- The [-90, 60] C bounds are far wider than any real ERA5 daily maximum but narrow enough to catch unit mix-ups and keying errors: a Fahrenheit-style 104 (about 40 C) and anything misread or sign-flipped is rejected. A units bug surfaces in the quality report as invalid_days instead of silently warping trends and thresholds.
- Partial years fail the 90% coverage rule by construction: coverage is scored against the full 365/366 days of the calendar year, not against the days present, so e.g. a July-to-December probe scores ~0.5 and is excluded. This protects threshold and trend statistics from years that are missing a whole season.
- ERA5 is documented as a gap-free reanalysis product, so for real data the gap count is expected to be near zero (the live 2000-2009 probe shows missing_days 0). The tests carry machine-checked proof that clean_daily both represents gaps when genuinely present and yields none for clean data.
- raw_daily BSON sizes (measured 2026-10-12 with bson.encode on a realistic doc for one cell-year): 4,938 bytes for a 366-float leap year with no gaps, 4,925 bytes for 365-float, 4,917 bytes for 365 entries with one null; a 24-byte ObjectId `_id` adds 34 bytes. A full 36-year cell history (1990-2025, 9 leap + 27 common years) occupies about 177,000 bytes, so roughly 3,026 such histories fit in Atlas M0's 512 MB - about 1.6 MB even for a 9-cell region x 36 years, i.e. storage headroom is irrelevant to product capacity planning.
- BSON datetimes store instants only. pymongo returns a datetime WITHOUT tzinfo (naive, in UTC) on read-back regardless of how it was written, and mongomock drops tzinfo the same way. storage writes fetched_at as a tz-aware UTC datetime (contract satisfied at the write boundary) and callers re-tag with `.replace(tzinfo=datetime.UTC)` after find().
- Mongomock 4.3.0 records the TTL index option (expireAfterSeconds appears in index_information) but does not enforce expiry; actual TTL deletion happens only on a real mongod/MongoDB server.
- mongomock 4.3.0 cannot execute `bulk_write` for update/replace operations under pymongo 4.18.3: pymongo passes `sort=` to mongomock's `BulkOperationBuilder.add_update()/add_replace()`, which rejects it (only InsertOne works). upsert_docs therefore performs one `replace_one(filter, doc, upsert=True)` per document keyed on key_fields, with every document validated before any write, so a batch is all-or-nothing in practice.
- The events unique index is (cell_id, hazard, start), NOT (cell_id, hazard, year): a calendar year can legitimately contain more than one heatwave, so a year-keyed unique index would silently forbid writing a second event of the same type in a year. annual_metrics keeps (cell_id, hazard, year) because it is one aggregated row per year by design.
- On mask slicing (Task 07): a Series remembers its attrs across slicing, but the stored mask arrays are full-span - `series["2001-01-01":"2001-12-31"].attrs["missing_mask"]` still has the whole-span length. Counts must therefore be produced by applying the per-year boolean directly to each mask array. Session probe (2026-10-12): a 10-day series sliced to 5 rows carried `missing_mask` of length 10.
- The suspect masks are computed in clean_daily and stored in attrs as bool arrays, exactly as the missing/invalid masks are, so ingestion derives {missing_days, invalid_days, suspect_days} per year without recomputation. `quality_report` now reads attrs' suspect_mask if present (identical formula fallback), so whole-series counts and the per-year sums still agree to the day.
- Leap-aligned day index: mapping every date to a slot 1..366 where Mar 1 is always 61 makes a threshold slot line up across leap and non-leap years instead of letting Feb 29 shift every later date by one day; the extra day lives only in slot 60 and only in leap years. Non-leap dates from Mar 1 onward take calendar day-of-year + 1 (verified against numpy 2.5.4 / pandas 3.0.6: 2019-03-01 -> 61, 2019-12-31 -> 366, 2020-02-29 -> 60, 2020-03-01 -> 61).
- Circular +/-7 slot window: pooling the 15 neighbouring slots smooths one day's sample, and wrapping modulo 366 gives slot 1 the same-sized sample as mid-year (it borrows slots 360..366 and 1..8). Without the wrap, the first and last week of the year would be estimated from far fewer values; the wrap is proven by the known-answer test where Dec 31 values pull the slot-1 threshold up.
- MIN_POOL=100: a slot whose pooled sample (years x 15 neighbours, NaN excluded) is below 100 is too thin for a stable 95th percentile, so it is emitted as NaN rather than a value built from too little data. A full 30-year baseline gives a pool of 450 before gaps, so the guard only bites on heavily gapped slots.
- MIN_BASELINE_YEARS=24 of 30: requiring 24 valid baseline years keeps at least ~80% of 1991-2020, so a threshold is never built from a decade of data posing as the baseline. Years are counted with the same 90% full-calendar coverage rule used everywhere else (reusing `cleaning.coverage_by_year` and `MIN_VALID_FRACTION`), so the two rules cannot drift apart.
- Threshold inputs outside 1991-2020 are filtered out, not rejected: ingestion stores 1990 onward, so `compute_thresholds` is normally handed more than the baseline and must ignore the extra years silently.
- Threshold performance: the whole baseline is shaped into one (years x 366) matrix and pooled with a single fancy-index plus reshape, so a 36-year series computes in ~0.05 s with no per-day Python loop.
- Event detection is a single array pass: `exceed = tmax > threshold(slot)` (strict; NaN on either side yields False), a continuation flag is true only when two adjacent days both exceed and their date delta is exactly one calendar day, and `cumsum(~continues)` turns the mask into run ids that pandas groups in one aggregation. There is no Python loop per day or per event.
- "A missing value breaks a run" falls out of the vectorised form rather than being special-cased: `NaN > x` and `x > NaN` are both False, so a NaN day is simply not an exceed day, and a NaN threshold (thin slot from Task 08) can never be exceeded. A gap in the index (a dropped date) gives a date delta of two days, so it also fails the continuation test. Never filled or imputed.
- Strict inequality is deliberate: a day exactly at the threshold is not a heatwave day, which matches "strictly greater than that day's threshold" and keeps event counts conservative against interpolation artefacts in the threshold itself.
- Year-boundary runs: continuation is decided by calendar-day adjacency, not by year equality, so Dec 31 -> Jan 1 stays one run; each event is stamped with the year of its start (`start.year`), matching "events assigned to the year of their start". This is also why ingestion keys the events collection on start date, not year.
- Intensity = mean of (tmax - threshold) over the event days, in Celsius. It measures how far above the local climatological threshold the event rose, so a hot cell and a cool cell can be compared on the same axis; raw peak/mean tmax would confound a warmer climatology with a more anomalous event.
- Event duration is a count of calendar days from start to end inclusive (equals the number of exceeding adjacent days because adjacency is enforced), so a run with an interior missing date or a gap is never counted as one longer event.
- Annual-metrics year validity reuses `cleaning.coverage_by_year` and `cleaning.MIN_VALID_FRACTION`, so the 90%-of-full-calendar rule keeps exactly one implementation; `total_days` and `valid_days` are reported alongside, and a test pins `valid == (valid_days / total_days >= MIN_VALID_FRACTION)` so the two representations cannot drift apart.
- Per-year panel is built as `pd.concat([...])` + `groupby(level=0).mean()`: invalid cells are NaN in every metric column (annual_metrics contract), so the per-metric NaN-ignoring mean automatically averages only the valid cells, while a valid zero-event cell contributes its explicit 0 to event_count/heatwave_days and nothing to intensity, max_exceedance or peak_tmax.
- `n_cells_valid` is a groupby sum over the cells' `valid` columns; a calendar year in the union that a cell never measured contributes nothing (that cell is uninvolved, not invalid). A region year is usable when `n_cells_valid / n_cells >= MIN_CELL_FRACTION`.
- Zero vs NaN in annual metrics: event_count and heatwave_days are 0 only for a *valid* year with no events; every metric including the counts is NaN for an invalid year even when events exist. Counts of zero would claim data the year lacks, so Task 11 must drop NaN years rather than average zeros over them.
- mean_intensity is the duration-weighted mean `sum(duration * intensity) / sum(duration)` of a year's events, computed from two groupby sums (no python loop, no auxiliary function). Weighting by duration makes intensity measure "how hot, for how long", which is comparable across years and cells on one axis.
- The calendar-year panel is `np.arange(first_year, last_year + 1)` — a year with zero rows inside the span appears as a present, invalid row (valid_days 0, metrics NaN), so no index gap exists. Edge years (a series starting Jul 1 or ending Mar 31) are judged against the full 365/366 days and are therefore normally invalid, with `total_days` still the full calendar length.
- Event attribution uses `events["start"].dt.year`, not the events `year` column, and events whose start year lies outside the tmax span raise `MetricsError` (corrupt input, not silently dropped).
- Trend slope and p-value come from different libraries on purpose. `scipy.stats.theilslopes(values, years)` gives Sen's slope against the actual calendar years, so a gap in the valid years changes the fitted rate. `pymannkendall.original_test(values)` gives the p-value. pymannkendall's own `sens_slope` ranks over integer positions 0..n-1, so with a non-contiguous series it would report a slope that ignores year spacing; the two libraries' slopes are not interchangeable once gaps exist. Verified by running both: a flat/step series over years 1990-1997 union 2003-2010 gives Theil-Sen 0.5556 per decade on real years vs 0.7692 on positions. A test pins `slope_per_decade == theilslopes(values, years).slope * 10` and that it differs from the positional slope.
- Mann-Kendall variant: `pymannkendall.original_test` is the original Mann-Kendall test with a tie correction in the variance of S (its private `__variance_s` subtracts `sum tp(tp-1)(2tp+5)` when duplicate values are present, which annual heatwave-day counts frequently are; verified by reading the installed 1.4.3 source). No pre-whitening or modified (Hamed-Rao/Yue-Wang) variant is used because those correct for serial correlation, a different question; the no-autocorrelation limitation is recorded for the README.
- Evidence bands are one-sided thresholds on p: p < 0.05 strong, 0.05 <= p < 0.15 weak, p >= 0.15 none. The weak band is conservative and is reported as "weak", never as a trend claim; the slope sign is attached to direction only once evidence is strong or weak, otherwise direction is "flat".
- Percent change uses the mean of the first five and last five valid years, not the endpoint years: one anomalous start or end year would swing an endpoint ratio by tens of percent, while five-year means absorb a single bad year. The ratio is suppressed when the first-period mean is below 1.0 day/year because a small denominator makes the percentage explode and mislead; the absolute change is reported instead (Task 12).
- Rolling mean uses a centred 5-year window with min_periods 3 over the full year index. Invalidity is NaN in that index (Task 10), so rolling over the index rather than over the compacted valid values keeps a NaN year in its own slot and stops it shifting the window's calendar alignment. With min_periods 3 a full-width edge window still holds the 3 positions pandas covers at a series boundary (verified on pandas 3.0.6), so an edge is NaN only when fewer than 3 of those positions are non-NaN - a short series or NaN edge years, exactly when a mean would misrepresent its neighbourhood.
- Non-contiguous valid years (e.g. a decade of failed coverage) enter the slope with their real year values, so a 5-year gap stretches the fitted rate instead of counting as one step; the p-value is rank-based on the chronological sequence of valid values. Trend validity (15 valid years) is counted after dropping NaN, never over calendar positions.
- Insight text is produced only from fixed templates in one module dict (`_TEMPLATES`); the builders fill named placeholders and never compose free text, so the same inputs always give the same sentences and no LLM or clock is involved. Every number in a sentence is read straight from the trend dict or region frame and formatted with a locale-independent spec (`:.1f`, `:.2f`, `:.0f`).
- Evidence licensing: only "strong" evidence may use a trend verb and a percent; "weak" is stated as weak and non-conclusive at caution level, "none" states that no clear trend was detected, and "insufficient" states the valid-year count against MIN_VALID_YEARS (imported from trends, never redefined). The wording is therefore never stronger than the statistics.
- Percent change and slope are printed as absolute magnitudes next to a direction word, so a decreasing result reads "decreased ... a 40% change" with no double sign. Percent uses Python's format rounding (40.5 -> "40", 40.6 -> "41"), which is deterministic and locale-free.
- Peak year is the valid-year row with the largest region-mean heatwave_days; ties go to the earliest year because the region index is chronological and `idxmax` returns the first maximum. An all-zero valid range reports "no <hazard> days in any valid year" instead of a year, and a range with no valid year omits the insight.
- The data-quality insight is always present and always carries the source credit "Data: ERA5 reanalysis via Open-Meteo"; it reports valid years out of total and the smallest n_cells_valid against the largest observed (the region's cell count inferred from the frame), with level caution when any year is invalid or cell coverage varies.
- Insight ordering is fixed (headline, intensity, peak_year, data_quality) and each insight dict lists key/level/text in that order; an insight is omitted only when its inputs are absent (intensity key missing, no valid year), never emitted empty.
- The analysis request model is deliberately flat (nine scalar fields) so Task 14 can declare it as `Annotated[AnalysisRequest, Query()]`. FastAPI delivers every query value as a string, so numeric request fields use pydantic's lax parsing (numeric strings coerce) with `allow_inf_nan=False`. Verified by running installed FastAPI 0.143.0: `?lat=28.6` parses, `?lat=abc` is a 422 ("Input should be a valid number"); strict float fields returned 422 for *every* query request, so "strict" here means only that non-numeric strings, NaN and infinity are rejected.
- Region is one of two shapes expressed in the same flat fields: a point is (lat, lon), a box is (south, west, north, east). Mixed or partial combinations and an absent region are rejected in a model validator. Degenerate boxes (south == north or west == east) are rejected here even though `regions.cells_in_box` permits them, because the API contract asks for south < north and west < east.
- Box-to-cells resolution reuses `regions.cells_in_box`/`cell_id`, so the 9-cell cap, the 0.25-degree snapping and the [-90,90]/[-180,180] bounds are enforced by the one implementation, never copied. The list is resolved once in a model validator into a private `_cell_ids` attribute exposed by the `cell_ids` property, so Task 14 resolves a region exactly once. A box of exactly 9 cells at the grid edge (89.5-90.0 N, 179.5-180.0 E) is accepted.
- Response models reuse the engine's own shapes: `TrendOut` is exactly the eight keys of `trends.trend`, `YearPoint` mirrors the `metrics.region_metrics` columns plus the `trends.rolling_mean` value, `attribution` is `insights.DATA_SOURCE`, and the insight levels are the "info"/"caution" pair. The trend dict is keyed by a two-member Literal (heatwave_days, mean_intensity) so an unknown metric name cannot appear.
- NaN safety is one shared annotated type (`NullableFloat`) whose before-validator turns any non-finite float into None; the engine's NaN metrics therefore serialise as JSON null and the whole response passes `json.dumps(..., allow_nan=False)`. This is the opposite of the request, which rejects non-finite coordinates.
- Error bodies are constrained at the model: `code` is a lower snake-case machine string and `message` is bounded and refused if it contains "http", "mongodb", a path separator or "traceback", so upstream URLs, DB URIs, file paths and stack traces cannot reach a client.
- The analysis is served from a three-layer cache: the `analyses` result doc (exact request keyed), the per-cell derived docs `thresholds`/`events`/`annual_metrics` (keyed by cell plus `computed_for_last_full_year`), and the raw `raw_daily` docs (keyed by cell-year). A warm request that hits the result layer does zero upstream calls and zero recompute; a new range on warm cells recomputes only the region aggregation and still makes no upstream call (live: warm 0.15 s / 0 calls, different range 0.74 s / 0 calls).
- `computed_for_last_full_year` is stamped on every derived doc and folded into the analysis cache key, so the year rollover on Jan 1 invalidates every stale derived doc and cached response at once instead of serving numbers computed against a different history length.
- Partial regions are computed but never cached: a response is stored only when every requested cell resolved (`len(usable) == len(cell_ids)`). This keeps the cache a record of complete analyses, so a later identical request can never be served a response built from a subset of cells; the cost is recomputing partial results.
- The analyzable-region rule reuses `engine.metrics.MIN_CELL_FRACTION=0.5`: at least `ceil(0.5 * n)` cells must resolve, otherwise the endpoint returns `data_unavailable` (502). A single dropped cell still returns a response, with `quality.cells` lowered and `min_cells_valid` reporting the shortfall.
- Failure isolation is per cell: a cell raising `ThresholdError`/`EventError`/`MetricsError`/`LookupError` is dropped, and `ingest_region` records upstream failures as `status="failed"`. One bad cell cannot fail a 9-cell region unless it pushes the usable count below the floor; any other exception (DB, upstream, ingest) propagates so a real infrastructure failure is never reported as a partial region.
- Synchronous inline ingestion (locked 2026-10-12 with the maintainer): a cold request ingests missing years inline. Live measurement is 17.4 s for 1 cell and 62.3 s for 4 cells (~15.6 s/cell), projecting ~140 s for 9 cells, which exceeds Render's 30 s sync timeout; this is recorded as a deployment risk (Open Issues) rather than solved here (background jobs, cache headers and rate limiting are Task 15+).
- The region label is the constant `REGION_LABEL="Selected region"` because the endpoint accepts coordinates only; Task 16 (presets) will supply a real place name, changing the insight text in one place.
- The HTTP handler maps typed exceptions to a safe body in a fixed precedence order (service `AnalysisError` first, then upstream/ingest, then data-quality, then DB, then region, then internal), so a specific code always wins over the generic 500 and engine message text (which may name files or modules) is never forwarded. `year_out_of_range` is 400 and `data_unavailable` is 502 (the data is missing upstream or at compute, not the caller's fault).

The design decision that took iteration to get right was the span contract: a dropped Feb 29 is real missing data, while an endpoint-truncated response is a transport failure, and the two need different handling (store vs raise). The interesting piece was the two-step "0 vs NaN" rule: I compute honest counts first and only then overwrite invalid years with NaN, so a zero never survives in a row that lacks the data to support it; that ordering is what the spec actually demands and it falls out cleanly. The region case taught me a subtlety I nearly got wrong in the tests first: a valid cell with no events contributes 0 to counts but nothing to intensity, and a cell that never measured a year contributes nothing at all (uninvolved, not invalid) - the difference shows up only under the "two cells with different spans and different valid years" probe. - Task 11: the one genuinely load-bearing discovery was that pymannkendall and scipy disagree about what "slope" means when years are missing - pymannkendall ranks over positions 0..n-1 while scipy takes the year vector - so the "use one library for both if possible" branch was closed, and I proved the split numerically (0.5556 vs 0.7692 per decade) rather than asserting it. The min_periods=3 wording also needed care: a centred 5-year window covers 3 positions at a series edge, so all-valid edges are computed, not NaN; the spec's "edges give NaN" is true only for short series or NaN edge years, and I recorded that instead of forcing min_periods=5 to match a phrase. The Theil-Sen outlier run - 29 fives and a 1000 - coming back at exactly slope 0.0 is the cleanest one-line argument for why the median estimator belongs under a climate series with bad years.

The pleasant surprise is that the required banned-word rule is nearly free - using a direction verb plus a source credit means "because", "caused", "will" and "significant" simply never have a reason to appear - so the test is a guard, not a writing rule. Three layers (result doc, per-cell derived docs, raw docs), each with its own freshness key, give a warm request 0.15 s and a new range zero upstream calls - which is the only reason synchronous ingestion survives for repeat traffic.
